# docs-writer.md — 文档写作

用于写、改 `README.md`、线内 `README.md`、接口/查询说明、报告章节与交付说明。通用风格见 `conventions/docs-style.md`，本文件管"写什么、按什么顺序写、写完怎么核"。

## 1. 写作前

1. 明确读者：组员（怎么跑）、教师（做了什么、怎么验证）、自己（两周后还看得懂）。
2. 把事实来源读一遍再动笔：`02_后端线/*.sql`、`03_前端线/README.md`、`00_分工与进度.md`。**不凭记忆写表名、字段、过程签名、数字。**
3. 确认这件事是否已有文档：已有就改那一处，不新建重复文档。
4. 新增文件前先看 `00_分工与进度.md` 的登记表，文件名与编号必须一致；未登记的文件不擅自创建。

## 2. 各类文档骨架

### 2.1 线内 README（如 `03_前端线/README.md`）

定位 → 技术选型 → 目录结构 → 环境准备 → 启动步骤 → 页面与功能清单 → 依赖的接口/存储过程 → 验证记录 → 已知问题 → 交付清单。

- 启动步骤必须是从零可复现的命令序列，写清前置条件与工作目录。
- 页面清单用表格：页面 / 路由 / 功能 / 依赖数据。
- 验证记录写实际跑过的结果，不写"预计"。

### 2.2 接口/查询说明

用途 → 入参表（名称、类型、必填、取值范围）→ 出参表（列名、含义、单位）→ 调用示例（可直接复制执行）→ 异常与边界 → 与数据库契约的对应条目。

- 存储过程必须写明 OUT 参数与每个返回码的含义，示例用真实签名（`CALL borrow_book(%s, %s, @p_result)`）。
- 示例里的日期、编号用测试数据里的真实值（`R001`、`C001`、`BR004`），不用 `xxx`、`123`。

### 2.3 报告章节

本节结论（2–3 句）→ 设计与实现要点（配 ER 图/页面截图）→ 验证方式与结果（条数、数字）→ 不足与改进（如实写：`init.sql` 字段未齐、续借次数无约束、逾期口径与原稿差异）。

- 截图放 `08_前端页面截图/`，文件名带页面与状态，正文用相对路径引用并配一句说明。
- 不复制代码全文进报告，只贴关键片段（不超过 20 行），并说明它解决了什么问题。

### 2.4 交付说明

见 `release.md` 第 3 节；交付说明本身要能被没参与开发的人读懂：装什么、跑什么、点哪里、看到什么算成功。

## 3. 事实核对（写完必做）

- [ ] 表名、字段名、状态值与 `02_后端线/*.sql` 一致
- [ ] 存储过程签名与返回码与 `05_存储过程.sql` 一致（不是照抄前端 README 旧稿）
- [ ] 数字能从仓库核对：6 表、10 读者、20 图书、30 副本、15 借阅、逾期当前 2 条
- [ ] 命令可执行：路径存在、虚拟环境步骤完整、端口未冲突
- [ ] 页面截图与当前实现一致（改了页面要重截）
- [ ] 无占位符、无 TODO 混进"已完成"、无人名与密码
- [ ] 引用其他文档用相对链接，链接目标存在

## 4. 修改既有文档

- 只改与本次变更相关的段落，不整篇重排（会产生无法审阅的 diff）。
- 删掉的内容若仍有价值，移到对应专题文档，不留在原地注释掉。
- 口径变化（如逾期清单定义）要同时更新：页面文案、SQL 注释、`db-contract.md`、报告章节；漏一处视为未完成。
- 在 PR 描述里说明"改了哪一段、为什么"，不写"更新文档"。

## 5. 禁止事项（硬性）

- 禁止编造测试结果、性能数字、数据量。
- 禁止写具体人名、学号、账号、密码；成员归属用"设计线/后端线/前端线"。
- 禁止把 `.agent/` 的内容复制进交付文档（那是开发期提示词，不是交付物）。
- 禁止提交带编辑器占位符（`<TODO>`、`xxx`、`待填`）的文档；未完成项统一写 `TODO(<模块>): <条件>`。
- 禁止在文档里贴与本仓库不符的命令或路径。
