# review.md — 代码与 SQL 审查

用于提交前自查、Review 他人改动、AI 预审。审查的目标是**找出会出错的地方**，不是证明代码好看。

## 1. 审查顺序（按此顺序，前面不过不必往后看）

1. **契约**：有没有改表结构、字段名、存储过程签名、状态枚举、报表口径？（对照 `conventions/db-contract.md`）
2. **正确性**：存储过程返回码是否逐分支处理？静默 0 行更新是否复查？分页/排序是否稳定？空结果是否处理？
3. **安全**：SQL 是否全参数化？模板是否对用户输入 `|safe`？密码/连接串是否进代码？
4. **口径**：报表数字的口径是否写明、是否与基线数据对得上？
5. **越界**：是否改了 `docs/`、`src/backend/sql/` 或他人文件？是否新增了未登记的文件？
6. **风格**：类型注解、docstring 三段式、命名、注释是否解释"为什么"。
7. **验证**：作者是否真的跑过？跑了什么、看到什么数字？

## 2. 输出格式（逐条，禁止笼统结论）

每条问题固定四段：

```
位置：src/frontend/app.py:88-96
现象：还书成功后直接提示"归还成功"，未复查 Borrow.status。
依据：db-contract.md 3.2 —— return_book 对不存在的 borrow_id 只更新 0 行、不报错。
建议：调用后 SELECT status, return_date 复查，status != '已归还' 时提示"该借阅记录不存在或已归还"。
```

- `位置` 用 `文件:行号`，行号必须真实。
- `现象` 只描述看到的事实，不夹带猜测。
- `依据` 指到具体规则或 `.sql` 文件与行；没有依据的偏好不写。
- `建议` 给可执行的改法，不写"建议优化"。
- 同一条问题出现多次时合并为一条并列出所有位置。

结尾给结论，只用三档：

| 结论 | 含义 |
| --- | --- |
| 阻塞 | 有正确性/安全/契约问题，必须改完再审 |
| 可合并，有建议 | 无阻塞问题，建议项可另开分支 |
| 通过 | 已按第 1 节全部检查，且作者提供了验证记录 |

**禁止只回 "LGTM"、"看起来没问题"、"整体不错"**；没有逐条检查就不给"通过"。

## 3. 前端专项检查清单

- [ ] 每个函数有完整类型注解与 `*Args:` / `*Return:` docstring
- [ ] 所有 SQL 参数化，`LIKE` 通配符在参数里
- [ ] 排序白名单生效，无用户字符串拼进 `ORDER BY`
- [ ] `borrow_book` 用三参调用并消费结果集，`@p_result` 每个码都有文案
- [ ] `return_book` / `renew_book` 有复查逻辑
- [ ] 写操作走 POST + 重定向，刷新不重复提交
- [ ] 模板无 `|safe`，链接用 `url_for`
- [ ] 报表口径在页面可见，数字与基线对得上
- [ ] 无明文密码、无 `.env`、无调试 `print`
- [ ] 只改了 `src/frontend/` 内的文件

## 4. 验证记录要求

作者需提供：

- 启动方式与版本（Python / MySQL / 驱动）。
- 跑过的操作与结果，例如"对 C004（`is_available=0`）借书 → 返回 -1，页面提示'该副本当前不在馆'"。
- 报表数字与基线核对结果（逾期清单应为 2 条：BR004、BR009）。
- 未验证的部分明确写"未验证 + 原因"，不写"应该没问题"。

## 5. 禁止事项

- 禁止无依据的主观偏好当问题提出（风格问题须引 `code-style.md` / `python-style.md` 条目）。
- 禁止虚构验证结果或引用不存在的行号。
- 禁止一次审查夹带无关改动（审查只读，改代码另开分支）。
- 禁止在他人 PR 里直接推自己的提交。
