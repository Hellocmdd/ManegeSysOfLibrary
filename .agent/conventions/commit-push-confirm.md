# commit-push-confirm.md — git 写操作确认协议

适用于 AI 助手与任何自动化脚本。读操作（`status`、`log`、`diff`、`show`、`branch -a`、`remote -v`）不需要确认；**写操作一律先请求确认**。

## 1. 需要确认的操作

`git add`、`git commit`、`git push`、`git merge`、`git rebase`、`git reset`、`git revert`、`git checkout -b` 之外的分支删除、`git stash drop`、`git tag`、修改 `.gitignore` 后重写索引、以及任何会改变他人可见状态的命令。

## 2. 确认请求格式

执行前必须先输出如下结构，**不得先跑命令再补说明**：

```
[待确认] <一句话说明要做什么>

变更范围：
- <文件路径>（<新增/修改/删除>，<行数或要点>）
- ...

执行命令：
- git add <具体路径>
- git commit -m "<拟用的提交信息>"

风险提示：
- <会不会影响他人分支 / 是否改写历史 / 是否可回滚 / 是否含敏感文件>

请确认：回复"确认"后执行；需要调整请直接说明。
```

- `变更范围` 必须逐文件列出，不用 `git add .` 这种笼统范围。
- `执行命令` 必须完整可复现，含引号与路径。
- `风险提示` 至少写一条；确实无风险时写"仅本地分支，未推送，可用 `git reset` 撤销"。
- **commit 与 push 分开确认**：commit 通过后，push 需再出一次确认，不合并成一步。

## 3. 同意的判定

- 只有明确肯定的回复才算同意：`确认` / `可以` / `同意` / `执行吧` / `好，push`。
- 以下**不算同意**，须重新等待：沉默、`看着办`、`你决定`、`应该没问题吧`、表情、只回了一个标点、转而讨论别的问题。
- 同意只对**当次**列出的命令有效；范围变了（多/少文件、改提交信息）要重新请求。
- 用户在确认里追加的修改意见，按下一条新请求处理。

## 4. 执行与回报

- 命令失败时**停止**，原样贴出错误输出，不做"换个方式再试一遍"的静默重试；涉及改写的操作（`reset`、`rebase`）失败时尤其要先报告。
- 成功后回报：提交哈希（短哈希）、提交信息、涉及文件数、当前分支、是否已推送。
- commit 后才发现范围错了：未推送可 `--amend`，需再确认一次；已推送用 `revert`，禁止改历史。

## 5. 本仓库的特殊约束

- `main` 是受保护分支，只接受 PR 合并；**永远不要**为 `main` 请求 push。
- 当前工作目录的 `.git` 在受限沙箱里不可写，git 写操作会报"访问被拒绝"/`Permission denied`。这不是命令写错，需要**申请完整权限**（`danger-full-access`）后重试，并在请求里说明"需要写 `.git`"。
- 提交前按 `git-workflow.md` 第 3 节自检；发现待提交清单里有 `.env`、`config_secret.py`、`__pycache__/`、`*.zip` 时立即停下并报告，而不是自行 `git rm --cached`。
- 交付 ZIP 不进仓库；需要交付时另行打包，不通过 git 分发。

## 6. 禁止事项（硬性）

- 禁止未出确认请求就执行任何 git 写操作。
- 禁止把 commit 与 push 合并成一次确认。
- 禁止在用户未确认时使用 `git add -A` / `git add .` / `git commit -a`。
- 禁止未经再次确认就 `--amend`、`rebase`、`push -f`、`branch -D`。
- 禁止在确认请求里隐瞒风险（如"会覆盖他人提交"）。
