## 1. 系统背景与业务范围

### 1.1 背景

图书馆需要管理读者、图书、馆藏副本以及借阅归还过程。手工或分散管理容易出现副本状态不一致、逾期难统计、借阅历史难追踪等问题。本项目以“图书馆管理系统”为选题，目标是设计一个能支撑上述业务的数据库，并用 Java/JDBC 命令行程序完成核心数据操作。

### 1.2 业务范围

纳入范围：

- 读者信息管理：注册信息、联系方式、账户状态
- 管理员信息管理：登录账号、角色、密码哈希
- 图书与分类管理：书目信息、多级分类、馆藏副本
- 借阅业务：借书、还书、续借、逾期判定
- 查询与统计：书目检索、借阅历史、热门图书、分类馆藏量、当前逾期、每月借阅量

不在范围：

- 预约履约、罚金支付、邮件/短信通知
- 复杂 Web 前端（课程任务书要求 Java 命令行程序；现有 Flask 页面仅作辅助演示）
- 多馆区、通借通还、读者信用评分

## 2. 系统用户角色及主要操作

| 角色 | 主要操作 |
| --- | --- |
| 读者 | 查询书目及可借副本、发起借书、查看个人借阅历史、发起归还/续借 |
| 管理员 | 维护读者、书籍、分类、副本信息；处理归还；查看统计报表 |

说明：`Admin.role` 的设计值来自现有关系模式（普通/超级），本报告沿用该字段定义。

## 3. 核心业务流程

### 3.1 借书

1. 读者发起借阅，提供读者编号与副本编号。
2. 系统校验读者状态为正常（`Reader.status = 1`）。
3. 系统校验副本在馆（`Copy.is_available = 1`）。
4. 系统校验该读者在借数量未达到上限（5 本）。
5. 写入 `Borrow` 记录，`borrow_date = CURDATE()`，`due_date = borrow_date + 30 天`，`status = '在借'`。
6. 将对应 `Copy.is_available` 置为 0。
7. 以上步骤必须在同一事务中完成，任一步失败则回滚。

### 3.2 还书

1. 管理员按借阅记录编号处理归还。
2. 写入 `return_date = CURDATE()`、`status = '已归还'`、`admin_id`、`handle_time = NOW()`。
3. 按当时是否超期写入 `is_overdue`。
4. 将对应副本 `is_available` 置为 1。
5. 存储过程可能静默更新 0 行，调用方必须复查记录状态后再提示成功。

### 3.3 续借

1. 仅允许 `return_date IS NULL` 的在借记录续借。
2. `due_date` 顺延 30 天，`status = '在借'`，`is_overdue = 0`。
3. 现有设计没有“续借次数”字段；是否限制次数为待确认需求。

### 3.4 查询与报表

- 按分类、书名等条件查询书目及可借副本数
- 查询读者借阅历史
- 热门图书 TOP10：按 `Borrow` 借阅记录数统计
- 各分类馆藏量：按分类统计副本数，空分类显示 0
- 当前逾期清单：`return_date IS NULL AND due_date < CURDATE()`
- 每月借阅量：按 `DATE_FORMAT(borrow_date, '%Y-%m')` 分组计数

## 4. 主要数据需求

| 数据对象 | 说明 | 对应表 |
| --- | --- | --- |
| 读者 | 编号、姓名、性别、电话、邮箱、注册日期、状态 | `Reader` |
| 管理员 | 编号、姓名、账号、密码哈希、角色 | `Admin` |
| 分类 | 编号、分类名、父分类编号（支持多级） | `Category` |
| 书籍 | 编号、ISBN、书名、作者、出版社、出版日期、简介、分类 | `Book` |
| 馆藏副本 | 编号、所属书籍、馆藏编号、存放位置、是否在馆 | `Copy` |
| 借阅记录 | 编号、读者、副本、借出/应还/归还日期、状态、逾期标记、经办管理员、处理时间 | `Borrow` |

## 5. 业务规则与数据约束

| 编号 | 规则 | 约束/实现位置 |
| --- | --- | --- |
| BR-01 | 管理员账号唯一 | `Admin.account` 唯一约束 |
| BR-02 | 管理员密码必须哈希存储，禁止明文 | 应用层写入；`pwd` 字段存 SHA256 |
| BR-03 | 分类支持多级，根节点父编号为空 | `Category.parent_id` 自引用外码 |
| BR-04 | ISBN 作为书目唯一标识 | `Book.isbn` 唯一约束（版本差异需确认） |
| BR-05 | 馆藏编号唯一 | `Copy.asset_no` 唯一约束 |
| BR-06 | 借书按副本进行，不直接借书目 | `Borrow.copy_id` 外码 |
| BR-07 | 禁用读者不得借书 | `Reader.status = 1` 校验 |
| BR-08 | 同一副本同时最多一条未归还记录 | `Copy.is_available` + 事务校验 |
| BR-09 | 读者在借上限 5 本 | 借书过程校验 |
| BR-10 | 借期固定 30 天 | 借书过程计算 `due_date` |
| BR-11 | 当前逾期口径为“未归还且已过应还日期” | 查询与报表统一口径；不得直接用历史 `is_overdue` |
| BR-12 | `Copy.is_available`、`Borrow.status`、`Borrow.is_overdue` 为冗余字段 | 由事务/存储过程/触发器维护一致性 |
| BR-13 | 删除有关联记录的主表数据应被阻止 | 外键 `ON DELETE RESTRICT` |
| BR-14 | 查询与写操作均需参数化 | JDBC `PreparedStatement` / Python 参数化游标 |

## 6. 明确需求、隐含需求与待确认需求

### 6.1 明确需求

- 至少 5 张核心业务表；现有设计为 6 张
- 支持借书、还书、续借、逾期统计
- 支持读者、书目、分类、副本、管理员信息维护
- 提供多条多表查询与分组统计
- 使用数据库事务保证借阅一致性

### 6.2 隐含需求

- 状态字段含义必须统一，前后端不得另造枚举值
- 冗余字段必须有明确的一致性维护机制
- 测试数据需满足参照完整性且覆盖正常/异常场景
- 密码等敏感信息不得写入仓库或提交给公共大模型
- 所有 AI 生成结果必须人工验证并留痕

### 6.3 待确认需求

1. **M:N 联系**：任务书要求至少包含一个多对多联系。现有设计说明称“读者—书”已通过副本与借阅记录分解为 1:N，因此没有 M:N。需向教师确认这种处理是否满足要求；若不满足，应补充“预约”等真正的 M:N 实体与中间表。
2. **续借次数**：现有 `Borrow` 表无续借次数字段，无法限制“只能续借一次”。需确认是否需要新增字段。
3. **分类馆藏量口径**：是否包含子分类馆藏，需在页面和报告中标注。
4. **每月借阅量**：没有借阅的月份是否补 0，需确认。
5. **数据库版本**：任务书写 MySQL 8.4 LTS 或 PostgreSQL 16，当前远程实例为 MySQL 9.7.2，差异已在 `docs/环境说明.md` 记录。
