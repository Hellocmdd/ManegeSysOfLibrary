# 范式检查说明

> 作者：张展博 · 2026-11-25
> 目标：所有关系模式达到 **3NF**。对故意反范式（保留冗余字段）的地方给出理由。

---

## 一、逐表检查

### ✅ Reader · 3NF
- 主键 reader_id
- 所有非主属性（name, sex, phone, email, reg_date, status）完全依赖主键
- 无传递依赖，无部分依赖 → **3NF** ✓

### ✅ Admin · 3NF
- 主键 admin_id
- account 单独建了 UK，pwd 存 SHA256
- 所有非主属性直接依赖 admin_id → **3NF** ✓

### ✅ Category · 3NF
- 主键 cat_id
- parent_id 是自引用外码，依赖关系明确 → **3NF** ✓

### ✅ Book · 3NF
- 主键 book_id
- cat_id 外码，依赖 Category.cat_id
- 所有非主属性直接依赖 book_id → **3NF** ✓

### ✅ Copy · 3NF
- 主键 copy_id
- book_id 外码
- is_available 虽然是冗余，但不影响范式（不是从 book_id 传递而来，而是从 Book 表可查询出来，但我们是**故意保留**的冗余字段）
- **3NF** ✓

### ✅ Borrow · 3NF（含冗余）
- 主键 borrow_id
- reader_id → Reader.reader_id
- copy_id   → Copy.copy_id
- admin_id  → Admin.admin_id（可空）
- borrow_date / due_date / return_date 直接依赖 borrow_id
- **注意**：status 和 is_overdue 是**故意保留的冗余字段**：
  - status 可由 return_date + is_overdue 推出（return_date IS NULL → "在借"，否则 → "已归还"）
  - is_overdue 可由 `due_date < CURDATE() AND return_date IS NULL` 推出
  - 我们选择保留它们，**不是因为范式要求，而是因为查询性能考虑**（直接用 WHERE status='在借' 比 JOIN + 时间比较高效得多）

---

## 二、冗余字段汇总（反范式 + 理由）

| 表 | 字段 | 为什么违反 3NF | 保留理由 | 一致性维护方式 |
|----|------|---------------|----------|----------------|
| Copy | is_available | 可由 Borrow 表 `COUNT(*) WHERE copy_id=? AND return_date IS NULL` 推出 | ① 前端"在馆/借出"一个字段直接筛选，性能好；② 借书事务里原子更新 | 存储过程 `borrow_book` / `return_book` 里 SET，事务保证原子性 |
| Borrow | status | 可由 return_date + is_overdue 推出 | 前端 `WHERE status='在借'` 直接筛选，报表快 | 存储过程 `borrow_book` / `return_book` / `renew_book` 里同步更新 |
| Borrow | is_overdue | 可由 `due_date < CURDATE()` 推出 | 表示"曾逾期"，用于历史标记 | `return_book` 按还书时是否超期写入，`renew_book` 归 0；当前无每日触发器，当前逾期报表不用该字段 |

**结论**：消除这三个冗余字段后，所有关系模式严格 **3NF**。保留它们是**查询性能优先**的工程决策，而非范式缺陷。

---

## 三、M:N 联系检查

本系统**不存在 M:N 联系**：
- "读者-书"本来是 M:N，但借书是借副本 → Borrow 表把它变成 1:N（读者→Borrow）+ 1:N（副本→Borrow）
- 副本→书是 1:N（一本书多个副本）
- 因此 ER→关系模式转换后**不需要额外中间表**

✓ 范式设计干净。
